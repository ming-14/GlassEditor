# Bug复盘：切换设置页开关导致程序崩溃且无任何日志

## 1. 现象

- 打开「设置」页，操作任意一个设置开关（如「减少动画」）后，程序**进程级崩溃退出**
- 日志文件里**没有任何报错**（连 ERROR/CRITICAL 都没有），看起来像"凭空消失"
- Windows 事件查看器只留下一条无堆栈的记录：`Application Error`，异常代码 `0xc0000409`

## 2. 根因

### 2.1 直接原因

`src/ui/main_window.py` 中槽函数的 `@pyqtSlot()` 装饰器签名与函数实际签名不一致：

```python
# 信号定义 (src/ui/settings_page.py)
settings_changed = pyqtSignal(dict)

# 信号连接 (src/ui/main_window.py)
self._settings_interface.settings_changed.connect(self._on_settings_page_changed)

# 槽函数：装饰器声明"零参数"，函数却要求 1 个参数
@pyqtSlot()                                    # ← 错误
def _on_settings_page_changed(self, settings: dict) -> None:
    self._action_manager._apply_shortcuts_from_registry()
```

`@pyqtSlot()` 会把该函数**注册为一个零参数槽**。信号发射时 PyQt5 按注册签名调用，
实际传入 0 个实参，于是抛出：

```
TypeError: MainWindow._on_settings_page_changed() missing 1 required positional argument: 'settings'
```

注意：**不是"减少动画"这个开关本身有问题**。设置页所有开关都通过同一个
`_on_auto_apply()` -> `settings_changed.emit(settings)` 链路，所以操作**任何**开关都会崩溃。

### 2.2 崩溃为何是"进程直接死"而不是弹异常

PyQt5 对槽函数中**未捕获的 Python 异常**的处理策略是：调用 `qFatal()` -> `abort()`。

- 进程以 `0xC0000409`（`STATUS_STACK_BUFFER_OVERRUN`，Windows 对 abort 的报告码）退出
- 这不是 Python 异常，`try/except` 和 `sys.exit()` 都无法拦截
- 表现为"闪退"，没有任何对话框

最小复现（可脱离本项目独立验证）：

```python
import sys
from PyQt5.QtCore import QTimer
from PyQt5.QtWidgets import QApplication

app = QApplication(sys.argv)

def boom():
    raise RuntimeError("boom-in-slot")

QTimer.singleShot(200, boom)
app.exec_()
# 运行结果：退出码 -1073740791 (0xC0000409)，stderr 为空
```

### 2.3 为什么"无任何日志"（这是本次最难排查的点）

日志系统 `src/infrastructure/logger.py` 只把异常记录在**主动调用 logger 的地方**，
而槽函数异常是 Python 解释器层面的未处理异常，走的是 `sys.excepthook`，
从不经过 loguru。因此日志里一片空白。

两个叠加因素让问题更难查：

1. **PyQt5 未安装自定义 excepthook 时不打印也不写文件**：实测该版本下 stderr 亦为空，
   异常信息彻底丢失。GUI 方式启动（无控制台）时更是完全不可见。
2. **文件 handler 使用 `enqueue=True` 异步写盘**，而 `abort()` 不会执行 `atexit` 刷新流程，
   即便在崩溃前打了日志也**可能丢失**（异步队列未落盘）。

## 3. 修复方案

### 3.1 修正槽签名（根因）

```python
@pyqtSlot(dict)                                # ← 与 pyqtSignal(dict) 保持一致
def _on_settings_page_changed(self, settings: dict) -> None:
    """..."""
    self._action_manager._apply_shortcuts_from_registry()
```

**规则：`@pyqtSlot(...)` 的参数必须与所连接信号的参数完全一致。**

### 3.2 安装全局异常钩子（杜绝"无日志"，兼防强杀）

在 `src/infrastructure/logger.py` 新增 `install_exception_hook()`，
并在 `src/main.py` 的 `start_logger()` 之后调用：

```python
def _log_unhandled_exception(exc_type, exc_value, exc_tb, source: str) -> None:
    if issubclass(exc_type, KeyboardInterrupt):
        sys.__excepthook__(exc_type, exc_value, exc_tb)
        return
    detail = "".join(traceback.format_exception(exc_type, exc_value, exc_tb))
    get_logger("Unhandled").critical(f"未处理异常[{source}]: {detail}")
    logger.complete()   # 关键：同步等待 enqueue 队列落盘，否则 abort 会丢日志
```

两个关键点：

- **`logger.complete()` 必须调用**。文件 handler 是 `enqueue=True` 异步写入，
  而崩溃路径不会执行 `atexit` 刷新，不加这一句崩溃日志照样会丢。
  （已实测验证：调用 `logger.complete()` 后紧接 `os.abort()`，日志内容成功落盘。）
- **安装自定义 `sys.excepthook` 后 PyQt5 不再 abort**。PyQt5 仅在 excepthook 为默认值时才走
  `qFatal()`；换成自定义钩子后，异常被接管，进程继续运行。
  于是本修复同时收获：崩溃有日志 + 单个槽出错不再拖垮整个进程。

同时挂载 `threading.excepthook`，覆盖子线程未处理异常。

## 4. 排查方法（同类问题通用）

### 4.1 先看退出码

| 现象 | 含义 |
|------|------|
| 进程无声消失、日志空白 | 优先怀疑**槽函数未捕获异常 -> `qFatal`/`abort`** |
| Windows 事件日志 `0xc0000409` | `abort()` 的典型报告码，不是内存越界 |

### 4.2 用 `_slot_audit` 式静态检查批量发现签名不匹配

`@pyqtSlot()` 的签名错误在**运行到该槽之前完全无症状**，务必静态扫描。
本项目用 AST 遍历全部 `@pyqtSlot` 装饰器，比对其声明参数个数与函数实际可接受参数个数
（排除 `self`，考虑默认值与 `*args`），一次性定位了唯一一处不匹配。

### 4.3 临时接管 excepthook 抓取真实堆栈

崩溃前把 `sys.excepthook` 指向一个写文件的函数，即可拿到完整 traceback：

```python
sys.excepthook = lambda t, v, tb: traceback.print_exception(t, v, tb, file=open("out.txt", "a"))
```

## 5. 教训

- **`@pyqtSlot()` 的签名不是注释，是契约**：漏写参数会导致"零参调用"，直接引发进程级 abort
- **Qt 槽异常不会自己进日志**：所有 GUI 程序都应默认安装 `sys.excepthook` + `threading.excepthook`
- **异步日志 + 崩溃 = 日志可能丢**：崩溃路径上写日志必须 `logger.complete()` 同步刷盘
- **"无日志"本身就是一类 Bug**：本次真正的排查成本不在修复（一行），而在定位——
  若早有异常钩子，这个问题 5 分钟即可定位
- **症状位置不等于病因位置**：用户报告"减少动画"开关，实际该页所有开关都会崩，
  应顺着信号链路上溯到连接点，而不是盯着开关本身的业务逻辑
