# 编码转换功能开发方案

## 0. 术语与范围

- **编码转换**：将当前打开文件的内容从其当前存储编码转换为另一目标编码，并以新编码写回磁盘，同时更新编辑器内的文本表示（文本内容保持不变，仅底层字节编码改变）。
- **涉及文件类型**：仅适用于已保存到磁盘的文件（有实际路径）。未命名的临时文件不支持编码转换（菜单项禁用）。
- **当前编码**：TabEntity.encoding 字段记录，也是文件实际存储的编码。打开文件时由 EncodingDetector 检测得出；用户手动转换后更新为该字段。

## 1. 功能详细设计

### 1.1 用户入口

#### 1.1.1 主菜单路径
**文件 → 编码 → [编码列表]**

- 编码列表分组（常用编码在上，其他在下）：
  - Unicode: UTF-8, UTF-8 with BOM, UTF-16 LE, UTF-16 BE
  - 简体中文: GBK, GB2312, GB18030
  - 繁体中文: Big5, Big5-HKSCS
  - 其他: Shift-JIS (日文), EUC-KR (韩文), ISO-8859-1 (西欧)
  - 传统编码: ASCII, Windows-1252
- 当前文件使用的编码在菜单中打勾（√ 或圆点）标识。
- 选择任一编码后立即触发转换流程。

#### 1.1.2 状态栏交互
- 状态栏编码区域当前显示格式：`UTF-8 ▾`（带下拉箭头）。
- 点击编码区域弹出一个快捷菜单，列出与主菜单相同的编码列表（避免重复定义，共用同一个 Action 列表）。
- 当前编码同样打勾标记，选择后触发相同转换逻辑。

### 1.2 转换前置条件与状态检查

| 条件 | 处理方式 |
|------|----------|
| 当前标签无文件路径（未命名） | 菜单项/状态栏编码按钮禁用，Tooltip 显示“保存文件后才能更改编码” |
| 文件以只读模式打开 | 菜单项禁用，Tooltip 显示“只读文件无法更改编码” |
| 文件有未保存的修改 | 自动先执行保存（静默保存，不弹出确认框），保存成功后再继续编码转换；如果保存失败（如磁盘满、权限不足），则终止转换并提示错误 |
| 目标编码与当前编码相同 | 不做任何操作，不弹提示 |
| 转换过程中发生编码错误（如某个字符无法用目标编码表示） | 终止转换，显示详细错误对话框，列出无法转换的字符位置（首几个），建议用户调整内容或尝试其他编码（如 GB18030 比 GBK 支持更全）。用户也可以选择强制转换，此时程序会清除不受支持的字符并继续 |
| 目标编码为 UTF-8 BOM | 写入文件时在开头添加 BOM (EF BB BF)，且状态栏显示 “UTF-8-BOM”；其他情况下不写入 BOM |
| 目标编码为 UTF-16 / UTF-32 | 自动处理 BOM（大端/小端），状态栏显示具体形式 |

### 1.3 转换流程（核心逻辑）

```
用户选择目标编码
       ↓
检查前置条件（路径存在、非只读）
       ↓
如有未保存修改 → 自动保存当前文件（原编码） → 保存失败则终止
       ↓
暂停文件系统监听（避免外部修改事件干扰）
       ↓
获取当前编辑器全文（Unicode 字符串）
       ↓
尝试将 Unicode 字符串编码为目标编码
       ├─ 成功 → 继续
       └─ 失败（UnicodeEncodeError）→ 恢复文件监听 → 显示错误对话框 → 终止
       ↓
以原子写入方式将编码后的字节流写回原文件路径
       ├─ 写入失败 → 恢复监听 → 显示错误（磁盘/权限）
       └─ 写入成功
            ↓
       更新 TabEntity.encoding 为目标编码字符串
            ↓
       重新加载文件（复用“重新加载”逻辑，但不清除撤销栈？决策见下文）
            ↓
       恢复文件监听
            ↓
       更新状态栏显示新编码
            ↓
       发送 SignalBus.file_encoding_changed.emit(path, new_encoding)
            ↓
       记录日志：INFO “文件编码转换: {path} from {old} to {new}”
```

### 1.4 关键设计决策

#### 1.4.1 转换后如何更新编辑器内容？
- **方案 A（推荐）**：不重新加载文件，直接设置编辑器文本（因为内容本身无变化），但需要刷新语法高亮、行号、书签等。此方案性能好，且保留撤销栈和光标位置。
  - 实现：编码转换成功后，编辑器文本不变，无需做任何额外更新。只需更新 TabEntity.encoding 和状态栏。文件系统上的字节已改变，但内存中的文本对象不受影响。
  - 潜在问题：如果编辑器中存在尚未保存的修改（但前置条件已要求先保存，所以此时内容与磁盘一致），没有问题。
- **方案 B**：完全重新加载文件（调用 TabManager.reload_current_tab）。会丢失撤销栈、光标位置、折叠区域等，用户体验较差，不采用。

**结论**：采用方案 A。编码转换本质是修改磁盘上文件的存储格式，不影响文本内容，因此编辑器不需要重新加载内容。但需要确保后续保存时使用新编码 —— 这通过更新 TabEntity.encoding 即可实现（FileService.save_file 将读取此编码来编码内容）。

#### 1.4.2 撤销栈处理
- 编码转换操作本身不应进入撤销栈，因为这不是对文本内容的编辑，而是元数据变更。用户按 Ctrl+Z 不应该“撤销编码转换”。
- 如果用户转换后再次编辑并保存，保存时使用新编码。撤销栈仍然有效（编辑操作可撤销）。

#### 1.4.3 并发与线程
- 编码转换可能涉及大文件（如 100 MB 文本），编码为 UTF-16 时内存占用增加。应放在**后台工作线程**中执行：
  - 步骤：获取编辑器文本（主线程，很快） → 将文本副本传递给工作线程进行编码 → 工作线程执行编码 + 原子写入 → 完成后通过信号通知主线程更新 UI。
  - 转换过程中显示模态进度对话框（“正在转换编码...”），可取消。取消时终止线程（需要设置中断标志）。
  - 由于编辑器文本可能很大，复制一份字符串到工作线程会有短暂阻塞，但可接受（比 UI 冻结好）。

#### 1.4.4 文件系统监听处理
- 保存期间必须暂停监听（已有实现）。编码转换中的写入阶段也应暂停，转换完成后恢复。

### 1.5 异常场景处理

| 异常 | 用户反馈 | 系统行为 |
|------|---------|----------|
| 目标编码不支持的字符 | 对话框显示：“无法转换到 {目标编码}，因为以下字符无法编码：{展示前5个字符及位置}。建议：使用 GB18030 等更宽编码，或修改文本。” | 转换终止，文件保持原编码，编辑器内容不变。不修改 TabEntity.encoding。 |
| 磁盘空间不足 | “保存失败：磁盘空间不足，请释放空间后重试。” | 原子写入失败，原文件保留，编码不变。 |
| 文件被外部程序锁定 | “无法写入文件，可能被其他程序占用。” | 同上。 |
| 用户取消转换（进度对话框） | 无错误提示，静默取消。 | 线程终止，不做任何修改。 |

### 1.6 支持的编码列表（完整）

为了提供全面的用户选择，应支持 Python `codecs` 模块中所有常用编码。动态生成菜单项（从预定义白名单 + 系统可用编码合并）。

白名单（按区域分组）：

```python
ENCODING_MENU_GROUPS = {
    "Unicode": ["utf-8", "utf-8-sig", "utf-16", "utf-16-be", "utf-16-le", "utf-32", "utf-32-be", "utf-32-le"],
    "简体中文": ["gbk", "gb2312", "gb18030"],
    "繁体中文": ["big5", "big5hkscs"],
    "日文": ["shift-jis", "euc-jp", "iso-2022-jp"],
    "韩文": ["euc-kr", "cp949"],
    "西欧": ["iso-8859-1", "iso-8859-15", "windows-1252"],

```

- 菜单中显示友好的显示名称（如 “UTF-8” 而不是 “utf-8”）。
- 对于带 BOM 的 UTF-8，显示名称为 “UTF-8 with BOM”，内部编码名称为 `utf-8-sig`。

```python
    """
```

#### TabManager.change_encoding_for_tab
```python
def change_encoding_for_tab(self, index: int, target_encoding: str) -> bool:

    对指定标签执行编码转换。

    """
```

#### SignalBus 信号
```python
file_encoding_changed = pyqtSignal(str, str)  # file_path, new_encoding
```

### 2.4 依赖关系检查

- UI 层调用 `ActionManager.change_encoding`（通过信号/槽）
- `ActionManager` 调用 `TabManager.change_encoding_for_tab`
- `TabManager` 调用 `FileService.change_encoding`（通过工作线程）
- `FileService` 依赖 `encoding_utils`（Infrastructure）
- 无逆向依赖，无循环导入，符合分层架构。

### 2.5 需要修改的现有流程

#### 2.5.1 文件保存时的编码来源
当前 `FileService.save_file` 可能依赖传入的 encoding 参数。在编码转换后，`TabManager` 应确保后续保存时使用新的 `TabEntity.encoding`。需要修改保存逻辑，使其从当前标签的 encoding 获取编码，而不是从某处缓存读取。

#### 2.5.2 状态栏编码显示更新
状态栏监听 `SignalBus.file_encoding_changed`，刷新显示文本。同时需要监听 `file_opened` 和 `tab_switched` 以更新当前编码显示。

#### 2.5.3 菜单项状态动态更新
`ActionManager` 需要监听 `tab_changed` 和 `file_encoding_changed` 信号，刷新“编码”子菜单中当前编码的打勾状态，并根据当前标签是否有文件路径、是否只读来启用/禁用菜单项。

## 3. 安全与性能自查

### 3.1 安全性

| 检查项 | 结论 |
|--------|------|
| 路径遍历 | 使用绝对路径，不拼接用户输入，安全 |
| 原子写入 | 已有 atomicwrites 保证，写入过程中断不会损坏原文件 |
| 临时文件泄露 | atomicwrites 自动清理临时文件 |
| 编码注入 | 无，编码名称来自白名单，不直接传递给系统命令 |
| 敏感数据 | 无新增敏感数据；日志中路径已脱敏 |
| 并发写入 | 转换期间暂停文件监听，且用户无法同时进行保存/转换（因为进度对话框模态阻塞） |

### 3.2 性能

| 场景 | 性能影响 | 缓解措施 |
|------|----------|----------|
| 大文件（> 10 MB）编码转换 | 编码操作 O(n)，可能造成 UI 卡顿 | 使用后台线程 + 进度对话框，用户可取消；编码过程不阻塞界面 |
| 转换后不重新加载编辑器 | 几乎零开销 | 方案 A 已避免重绘整个编辑器 |
| 获取编辑器全文 | 对于超大文件（> 100 MB），`toPlainText()` 会复制整个字符串，内存占用翻倍 | 限制：对于 > 50 MB 文件，禁用编码转换并提示“文件过大，暂不支持编码转换” |
| 编码错误检测 | 需要扫描全文才能发现不支持的字符 | 先尝试编码，若失败，再通过逐字符定位错误位置（仅用于错误报告，不影响主流程）。定位错误时可用二分法提高效率。 |

### 3.3 边界条件与限制

- 文件大小 > 50 MB：禁用编码转换菜单项，提示“文件过大，编码转换可能导致内存不足”。
- 编码转换期间用户关闭标签：取消工作线程，放弃转换。
- 同时打开多个分屏且同一文件在多分屏中显示：转换后只需更新 TabEntity 和状态栏，其他分屏的内容会自动同步（因为共享同一编辑器实例？需要确认多分屏的实现：通常每个分屏是独立的编辑器实例，但指向同一个底层文档模型。如果采用共享文档模型，转换后所有分屏都能看到相同内容；如果各自独立，需要广播同步。根据《交互设计说明》7.2节：“一个分屏中修改实时反映到其他分屏”，说明它们共享内容。因此转换后不需要额外处理）。

## 4. 测试要点

### 4.1 功能测试

1. 打开 UTF-8 文件，转换为 GBK → 文件保存为 GBK，状态栏显示 GBK，重新打开文件以 GBK 正常显示。
2. 转换时选择 UTF-8 with BOM → 文件头部增加 BOM，状态栏显示 UTF-8-BOM。
3. 文件包含 emoji 😊，尝试转换为 GBK → 弹出错误对话框提示，显示无法编码的字符及位置，文件保持原样。
4. 未保存的文件 → 编码菜单禁用；保存后再启用。
5. 只读文件 → 菜单禁用。
6. 从状态栏切换编码 → 行为与菜单一致。
7. 转换过程中点击取消 → 无变化，文件未修改。
8. 转换前后编辑撤销栈不受影响。
9. 会话保存后重启 → 编码信息恢复正确，状态栏显示正确。

### 4.2 异常测试

- 磁盘满 → 转换失败，显示错误，原文件完好。
- 文件被外部锁定 → 失败提示。
- 目标编码名称为空/无效 → 菜单中不会出现无效项，无需测试。
